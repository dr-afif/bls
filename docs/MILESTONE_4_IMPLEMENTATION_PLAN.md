# Milestone 4 Implementation Plan

## Outcome

Replace the authenticated learner Guides, instructor Teaching Kit, resource
viewer, and administrator Resources placeholders with a secure, versioned
resource system backed by Supabase. Preserve the separate `/demo` routes and
their local fictional repository.

This milestone remains a companion for a physical BLS course. Resources are
quick references and teaching materials, not lessons, modules, completion
gates, or a self-paced learning path.

## Scope

### Included

- Organization-scoped resource metadata and immutable versions
- Learner and instructor audience assignment
- BLS topic and teaching-stage taxonomy
- Draft, review, approval, publication, retirement, and archive states
- Private PDF storage with immutable version-specific object paths
- Authenticated, entitlement-checked, short-lived PDF access
- Resource access and administrative audit events
- Authenticated learner Guides and instructor Teaching Kit
- Accessible guide, checklist, video, and protected-document viewers
- Administrator resource list, editor, version history, review, and publication
- Table, Storage, function, repository, component, and browser tests

### Excluded

- Quiz or result implementation
- Resource-completion requirements or progress dashboards
- Fully offline protected resources
- Public Storage buckets or permanent file URLs
- Claims of absolute download, print, screenshot, or recording prevention
- Automated clinical-guideline review reminders
- Real learner or clinical production data

## Decisions for this milestone

1. Use the existing React, TypeScript, Vite, TanStack Query, Tailwind v3, and
   source-owned Radix/shadcn-style component foundation.
2. Keep `/demo` data local. Add a separate production `resources` feature with
   typed Supabase repositories and query hooks.
3. Treat an active account plus an active, organization-matching course/cohort
   entitlement as the server-side resource-access boundary.
4. Store PDFs in one private `course-resources` bucket. Use a unique path per
   immutable version; never overwrite a published object.
5. Issue PDF access through an authenticated Edge Function. It must validate
   the caller and version entitlement, create a short-lived signed URL with a
   server-only secret key, and append an access audit event.
6. Keep Edge Function JWT verification enabled. The frontend sends the signed-in
   user's JWT through `supabase.functions.invoke`; use the current
   `@supabase/server` user-auth wrapper inside the function and keep the
   publishable key in the separate `apikey` header.
7. Treat unlisted YouTube identifiers as obscured rather than protected. Keep
   the video provider behind a small adapter so it can be replaced later.
8. Store guide/checklist content as an immutable structured `jsonb` snapshot in
   each version. This is an intentional exception to the normalized-data
   preference because the content is versioned and historical.
9. Do not expose a service-role or secret key to the browser, repository,
   GitHub Actions variables, or generated frontend assets.

## Proposed database model

Create all schema changes through migrations generated by the Supabase CLI.
Use UUID primary keys, `timestamptz`, explicit foreign-key delete behaviour,
constraints, indexes, grants, RLS, and generated TypeScript types.

### Taxonomy

- `bls_topics`: organization, slug, name, description, display order, active
- `teaching_stages`: organization, slug, name, description, display order,
  active
- Seed fictional Adult BLS topics and stages matching the approved prototype.
- Taxonomy records are retired rather than deleted once referenced.

### Course access

- Add the minimal `courses` record needed for the single Adult BLS format.
- Associate cohorts with a course.
- Add `course_entitlements` with user, course, optional cohort, start, expiry,
  status, grant/revoke metadata, and audit triggers.
- Seed fictional entitlements for the existing learner and instructor accounts.
- Centralize effective-access evaluation in a private helper used by table RLS
  and the access function.

### Resources

- `resources`: organization, course, stable title/slug, type, lifecycle status,
  estimated minutes, featured flag, availability window, current version,
  creator/updater, and timestamps
- `resource_versions`: resource, monotonically increasing version number,
  title, summary, structured content, YouTube identifier or private storage
  path, content hash, guideline source/year, review dates, reviewer/approver,
  state, creator, and creation timestamp
- `resource_audiences`: resource plus learner/instructor audience
- `resource_topics`: resource plus BLS topic
- `resource_teaching_stages`: resource plus teaching stage
- `resource_relations`: ordered related-resource links with no self-reference
- `resource_access_events`: append-only user, resource, version, action, request
  identifier, safe metadata, and timestamp

Use constraints to require exactly the appropriate content locator for each
resource type. Version rows are never updated or deleted through browser roles;
editing creates a new version. Publication atomically selects an approved
version as `current_version_id` and changes the resource state.

## Authorization and audit policy

### Anonymous users

- Cannot read resource metadata, versions, taxonomy, entitlements, events, or
  Storage objects.

### Learners

- Can read only published, currently available learner resources in their
  organization and course when effective entitlement is active.
- Cannot read draft/review versions, instructor-only resources, other
  organizations, raw access-event history, or administrative fields.

### Instructors

- Can read published instructor resources for courses connected to an active
  assigned cohort and may also read resources explicitly shared with learners.
- Cannot publish, edit versions, or read resources for unassigned courses.

### Administrators

- Can manage resource metadata, taxonomy assignments, versions, review state,
  and publication only inside their organization.
- Publication, retirement, audience changes, version creation, and Storage
  uploads create audit events.
- Published versions and their Storage objects cannot be overwritten or
  destructively removed by normal administrators.

### Privileged operations

- Use a narrowly scoped publication RPC for the atomic publication transition.
- Revoke default function execution from `PUBLIC` and `anon`; grant only the
  required authenticated role and perform explicit active-admin checks.
- Use one authenticated Edge Function for signed PDF access. Any admin client
  used inside it is limited to signing the already-authorized object and
  appending the corresponding audit event.

## Private Storage design

- Bucket: `course-resources`, private
- Allowed PDF MIME type and conservative maximum file size configured on the
  bucket
- Object key pattern:
  `<organization-id>/<resource-id>/<version-id>/<random-id>.pdf`
- Authenticated administrators may insert new objects only into their own
  organization path and only for a matching draft version.
- Browser roles receive no public URL and no broad object-list permission.
- Normal administrators cannot update/upsert an existing version object.
- Learner/instructor downloads are issued as short-lived signed URLs only after
  the Edge Function validates effective access.
- Signed URLs, PDFs, and protected viewer responses are excluded from service
  worker caches.

## Frontend organization

Add `src/features/resources/` with:

- `model/resource-types.ts`
- `data/resources-repository.ts`
- `data/resource-access-service.ts`
- `hooks/use-resources.ts`
- shared list, filter, status, metadata, related-resource, and viewer components
- learner Guides pages
- instructor Teaching Kit pages
- administrator resource list/editor/version/review pages

Keep repository errors as stable application error codes and map them to safe,
role-appropriate messages. Do not show raw Supabase, Storage, or Edge Function
errors.

### Learner and instructor experience

- Preserve topic-first learner browsing and stage-first instructor grouping.
- Keep search and filters in local URL-compatible state where practical.
- Keep common resources within one or two taps.
- Preserve route-focus management, skip navigation, visible focus states,
  semantic headings, 44-pixel targets, non-colour-only statuses, and responsive
  single-column lists.
- Viewer states: loading, unavailable, access denied, expired, offline, and
  recoverable error.
- PDF viewer uses a visible user-specific watermark and removes normal download
  and print controls while truthfully stating that copying cannot be prevented.
- Videos include captions/transcript support and never autoplay with sound.

### Administrator experience

- Desktop-first resource table with mobile cards
- Search and filters for audience, topic, teaching stage, type, publication
  state, and clinical-review state
- Full page or drawer editor; do not use a small modal for complex editing
- Version history is visible and immutable
- Publication checklist makes missing audience, taxonomy, content, guideline,
  reviewer, and review-date requirements explicit
- Destructive/retirement actions are separated from primary actions and require
  confirmation

## Required test matrix

- Anonymous access is denied everywhere.
- Suspended, expired, and revoked users cannot access resources.
- Learners cannot read instructor-only or unpublished resources.
- Instructors cannot read resources for unassigned courses.
- Cross-organization reads and writes fail.
- Administrators cannot manage another organization's records or object paths.
- Published versions cannot be mutated or deleted.
- Direct private-bucket URLs fail.
- Signed access requires a valid user JWT and effective entitlement.
- Signed URLs use a short expiry and each issuance is audited.
- Access-event inserts cannot be forged by browser clients.
- Search, filter, empty, loading, offline, expired, denied, and error states are
  accessible.
- Keyboard navigation, route focus, headings, touch targets, reflow, captions,
  and watermark legibility meet the documented accessibility requirements.

## Exit criteria

- Learners and instructors can reach permitted resources within one or two
  taps without encountering LMS-style sequencing.
- All browser-accessible tables and Storage paths have tested server-side
  authorization.
- Protected PDFs are private, short-lived when shared, visibly watermarked,
  and absent from service-worker caches.
- Published resource history is immutable and clinically reviewable.
- Material administrative actions and signed-access issuance are auditable.
- All required frontend, database, function, security, and deployed smoke tests
  pass with no critical findings.
